# ADR 0004: Local configuration UI

- Status: Accepted
- Date: 2026-08-03

## Context

Printer names, label stock, PDF scaling, polling cadence, and enabled print actions were initially edited in JSON. That remains a useful portable format, but it is unnecessarily error-prone for routine operation. The first deployment is still a trusted, single-user process on one machine; it does not need remote administration, user accounts, or a browser-delivered seller session.

## Decision

- Serve a small configuration UI from the application process on a loopback address only. Do not bind it to the LAN or public network.
- Keep versioned JSON as the canonical non-secret configuration. The UI is an adapter that reads, validates, and atomically replaces that file; it does not introduce another settings database.
- Discover installed Windows printer queues through the operating system and present their exact names as selections. Preserve the existing configured name when a printer is temporarily unavailable.
- Model whether an output runs as an `enabled` property on every action. Rules remain responsible for deciding _when_ an enabled action applies; disabling an action suppresses it globally without editing every rule.
- Show controls from action and printer capabilities. Address-label actions expose stock size, margin, and font size. Windows PDF printers expose DPI and scaling. This pattern can render future action types without coupling the workflow to these first two outputs.
- Never expose seller credentials or session material through the UI or its API. Limit request sizes, require same-origin writes, reject non-loopback hosts, and send a restrictive content security policy.
- Use a configuration revision hash so a stale browser tab cannot overwrite a newer edit. Validate the complete resulting application configuration before replacing the file.
- Host the UI with the long-running scheduler and also provide a `configure` command that runs the settings UI without seller credentials or synchronization.
- Build the browser client as typed Preact components with Vite. Keep server transport in a single browser API module, shared draft state in context providers, workflow pages in `src/web/pages`, reusable controls in `src/web/components`, and visual tokens/layout rules in focused style sheets. The server serves only the compiled, hashed application assets; do not return application-scale HTML, CSS, or JavaScript string literals from server modules.
- Organize the growing operator surface into Dashboard, Orders, Add cards, Inventory, Settings, and Jobs pages in a persistent left navigation rail. Dashboard is the default and shows ready-to-ship order summaries, aggregate product/shipping/order values calculated from those summaries, and compact enable/disable mirrors for address-label and packing-slip automation. Do not fetch per-order details for Dashboard metrics or rows. Reuse an already-loaded Orders list to derive the ready-to-ship view, and reuse loaded Dashboard state on ordinary page visits; only the explicit Refresh control bypasses that browser state. Orders shows the last three months of order summaries and explicit per-order fulfillment actions. Preserve TCGplayer order-status labels verbatim for display and never overlay an application-created provider status. Enable Mark shipped only from the private API package's normalized `SellerOrderStatus.ReadyToShip` code; unrecognized labels remain `SellerOrderStatus.Unknown`. Require an additional browser confirmation before Mark shipped by default, expose one persistent Settings toggle that disables it for both Dashboard and Orders, and default older configuration files to confirmation enabled. After a successful shipment mutation, invalidate both browser order views and reload the active view from the provider; if that read is briefly stale, display it honestly rather than fabricating a transition. Keep persistent polling, detailed printing, and background-worker configuration in Settings; keep action inputs with their workflows; and reserve Jobs for queue history and controls on individual jobs. Paginate card-addition and price-update histories independently at ten jobs per page. Allow only definitively failed jobs to be resubmitted, creating a new pending job with retry lineage while retaining the failed audit record; prevent duplicate resubmission of the same failed attempt and keep ambiguous `review-required` jobs non-retryable. Preserve each visited page's component state while navigating, expose the selected page in the URL hash, and use standard links for keyboard navigation. Treat the former `automation` hash as `settings` and the former `repricing` hash as `inventory` for compatibility.
- Read order lists on demand through a short in-memory cache. Never persist buyer names, addresses, order amounts, or packing-slip bytes, and never include them in logs. Download documents directly to the requesting browser. Require same-origin requests for printing, tracking, and shipment mutations. Manual shipment changes remain explicit operator actions and do not become part of the scheduled fulfillment workflow.
- ADR 0017 adds Scanner as a separate opt-in workspace. It reads the shared ready snapshot for local status and performs an authoritative refresh only after a confirmed tag. Scan-triggered automatic shipment mutation is governed by its own explicit setting and durable ledger; it does not become a scheduled fulfillment rule action.
- Treat third-party shipping handoffs as explicit operator actions. For Pirate Ship, confirm the seller-scoped order on demand, keep its address in the same short in-memory cache, copy a multiline address through the browser clipboard, and open the address-free Single Label URL. Never place customer data in query parameters, fragments, browser history, or logs. Fall back to a visible manual-copy prompt when clipboard permission is unavailable; do not add a browser extension or automate another site's DOM.
- Compare the current persistent-settings projection with the last server-loaded or successfully saved projection. Keep the fixed save banner hidden when they match, including when only preview/search fields change, and show it across tabs while persistent settings are dirty.

## Consequences

Routine printer and worker setup no longer requires hand-editing JSON, while configuration remains inspectable, portable, and compatible with the CLI. The operator console uses a full-height navigation rail, compact work surfaces, page-local scrolling, and dense tables instead of a document-style stack of cards. Distinct workflows no longer form one continuously scrolling page, action pages are not cluttered with persistent configuration, and changing pages does not discard searches, previews, selections, or unsaved settings. Frontend compilation is now a required build step and adds Preact/Vite development dependencies, while the deployed server remains dependency-light and serves static assets under the same loopback and CSP boundary. Dashboard and Orders may show data from the brief cache until refreshed. Printer discovery is Windows-specific in this release; other operating systems can add discovery adapters later. A saved configuration is used by one-shot commands immediately and by the scheduler on its next synchronization cycle. Remote and multi-user administration remain out of scope.
